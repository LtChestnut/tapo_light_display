# CLAUDE.md

Firmware for a Guition **JC3636K518** ESP32-S3 round knob display that controls 3 × TP-Link Tapo **L530E** colour bulbs directly over the LAN, using the Tapo KLAP protocol. Standalone: no Home Assistant, hub or cloud at runtime. The full hardware reference and pin map are in [README.md](README.md).

> The user originally called the bulbs "L350E". LAN discovery shows they are **L530E(EU)**: colour plus tunable white, KLAP v2 (`lv: 2`), HTTP on port 80. The network also has an L530B bulb and an H100 hub, which are not controlled.

## Toolchain (decided)

- PlatformIO in VS Code, using the **pioarduino** platform (Arduino-ESP32 **3.x**). Do not switch to the official `espressif32` platform: it ships Arduino 2.x, which the vendor display stack doesn't build on.
- LVGL **8.4.x**, not 9.
- The display libs come from **git tags**, not the PlatformIO registry, which only has stale 2023 builds. The versions are pinned to satisfy each other's `depends=`: `ESP32_Display_Panel` v1.0.1, `ESP32_IO_Expander` v1.0.1, `esp-lib-utils` v0.1.2. The vendor bundle's IO_Expander 1.1.0 needs esp-lib-utils ≥0.2, which conflicts with Display_Panel 1.0.1. The legacy `ESP_Panel*` names compile, with deprecation warnings only.
- `ArduinoJson` 7.
- Windows host. The shell tools are PowerShell and Git Bash; quote paths, since `Resources/` has spaces and Chinese filenames.

## Commands

`pio` is not on PATH; use `~/.platformio/penv/Scripts/pio.exe`.

```
pio run                                  # build
pio run -t upload --upload-port COM7     # flash + auto reset
pio test -e jc3636k518 --upload-port COM7 --test-port COM7   # on-device KLAP tests
```

Flashing the test overwrites the app; re-run `pio run -t upload` afterwards. To read the serial log without an interactive terminal, open COM7 with pyserial from `~/.platformio/penv/Scripts/python.exe`. The USB CDC port disappears on every reset, so reopen it in a loop.

## Flashing gotchas

- **USB-C orientation selects the chip.** "USB Serial Device", VID:PID **303A:1001**, currently COM7 = ESP32-S3, the target. "CH340" = secondary ESP32, which we never flash. If upload reaches the CH340, tell the user to flip the plug.
- The base's power switch must be ON (slid left).
- esptool's default `--after hard_reset` does an RTC-WDT reset on native USB. The port vanishes and pySerial throws "Cannot configure port", so PIO reports a successful flash as FAILED. That's why `platformio.ini` sets `board_upload.after_reset = no_reset`, and `scripts/reset_after_upload.py` pulses RTS instead. If you see "Hash of data verified", the flash worked.

## Hardware gotchas

- Display: ST77916 QSPI at 50 MHz needs the vendor init table and `invertColor(true)`.
- The draw buffer lives in internal DMA RAM (72 rows). Large buffers go in PSRAM (`MALLOC_CAP_SPIRAM`).
- The knob (measured with an edge trace, 2026-11-07): each detent is **one long low pulse on one pin**: GPIO8/A = clockwise, GPIO7/B = anticlockwise, 24–300 ms depending on speed, idle high. When that pin releases, the *other* pin gets a ~0.1 ms burst of crosstalk spikes ~0.2 ms later. Two earlier edge-interrupt decoders were fooled by those spikes: "each pin = a direction, count every fall" and "leading pin + trailing partner". The vendor 3 ms poller dropped clicks. `hal.cpp` now samples both pins at **1 kHz** (esp_timer): 3 consecutive low samples = one detent, re-arm after 3 high samples. Don't go back to edge interrupts for counting.
- There's a second identical switch (EC2) wired to the *secondary* ESP32, not the S3.
- Touch CST816S (IC id 182) and haptic **DRV2605L** (0x5A, id 7, LRA, open-loop) share I2C port 0 (SDA 11 / SCL 12). The display lib installs the **legacy** I2C driver there, so talk to the DRV2605 with `i2c_master_write_to_device(I2C_NUM_0, …)`. Never use `Wire` (the new driver conflicts). The DRV answered without GPIO38, so the user's board is **V2.0**.
- Gesture thresholds are set on the touch `lv_indev_drv_t` (`gesture_limit` 30, `gesture_min_velocity` 2). LVGL 8.4 hard-codes the `LV_INDEV_DEF_GESTURE_*` macros, so `lv_conf.h` can't change them.

## Power (from schematics V1 `JC3636K518_Power.png` + V2 sheet 1)

- Base board: USB-C VBUS → TP4055 Li-ion charger (~600 mA, R65 1.6 k) → battery on CN3 (JST 1.25 mm 2-pin). Power path: VBUS via Schottky D2, or VBAT via P-FET Q1 when unplugged → slide switch → main board "5V" rail. **There is no boost**: on battery the "5V" rail is VBAT (3.0–4.2 V), and a TLV62569 buck makes 3V3.
- GPIO1 = "5V" rail / 2 (10 k/10 k, a constant ~200 µA drain). It reads VBAT when unplugged and ~4.5 V on USB. The charger status pin is not wired to the S3, so we can't tell charging from charged.
- Always-on loads on the rails: the **secondary ESP32** (stock firmware runs Bluetooth audio, the biggest drain), CH340, PCM5100A DAC + its LDO, PDM mic, 3V3 buck Iq, the ADC divider. The S3 can't power-gate any of them.
- Wake sources for deep sleep: GPIO7/8 (knob, RTC GPIOs, ext1 ANY_LOW) and GPIO9 (touch INT).
- The vendor demo `ST77916_LVGL_DEMO/pincfg.h` has wrong SD pins. Trust the schematics and README.

## Sleep (src/config.h, ui.cpp, lights.cpp, hal.cpp)

- Screen off after `SCREEN_TIMEOUT_MS` (20 s) idle, with Wi-Fi modem power-save on. Deep sleep after `DEEP_SLEEP_AFTER_MS` (45 s) idle, once `lights::idle()` says nothing is pending, and only on battery unless `DEEP_SLEEP_ON_USB=1`. USB is detected as supply ≥ 4.30 V.
- Before deep sleep: `lights::prepareSleep()` parks the service task and copies the bulb cache, KLAP sessions (`KlapSession`, expiry in `time()` seconds, which keep counting through deep sleep) and AP BSSID/channel into `RTC_NOINIT` memory (raw bytes + magic). Then `hal::deepSleep()`: backlight off **and GPIO47 held low** (`gpio_reset_pin` off LEDC, `gpio_hold_en` + `gpio_deep_sleep_hold_en`, released in `initBacklight`). It's a digital pin, so without the hold it floated in deep sleep and the backlight came back on over a frozen frame (the bug fixed in v1.1). Next, ST77916 DISPOFF 0x28 + SLPIN 0x10 sent raw on the QSPI IO (`(0x02<<24)|(cmd<<8)`), because the driver's `esp_lcd_panel_disp_sleep` returns "not supported". Then DRV2605 standby, CST816S deep sleep (0xE5=0x03, unless `TOUCH_WAKE`), ext1 ANY_LOW wake on GPIO7/8 (+9 with touch wake). A knob pin still low after 1 s is left out of the mask, so a pin stuck low can't cause an instant-wake loop. `[ui] screen on: <reason>` / `screen off` lines log every backlight change.
- Wake = reboot with cause EXT1. The wake pins are still on the RTC mux, so `initKnob()` calls `rtc_gpio_deinit`. A knob pin already low at boot is the waking twist and isn't counted. UI page/mode use `RTC_DATA_ATTR`.
- Measured (bench, 2026-11-07): UI up ~0.93 s after the twist; Wi-Fi up at 4.4–7.2 s (the cached-AP `WiFi.begin(..., channel, bssid)` failed once and fell back to scanning); first command ~0.6–0.8 s after Wi-Fi. A couple of "no HTTP status" errors on the first requests after wake. Root cause found: **DHCP took ~5 s** on this router. The fix is an optional fixed IP (`KNOB_IP`/`KNOB_GATEWAY`/`KNOB_SUBNET`/`KNOB_DNS` in `secrets.h`; the LAN is a /22, so 255.255.252.0), `WiFi.persistent(false)`, and starting `lights::begin()` before `hal::begin()` so Wi-Fi joins while the LCD initialises. Cold boot now: radio 295 ms, associated 475 ms, Wi-Fi up 497 ms, UI up 1066 ms. `[wifi]` event lines log each stage.
- Bench-test sleep over USB: `PLATFORMIO_BUILD_FLAGS="-DDEEP_SLEEP_ON_USB=1 -DSCREEN_TIMEOUT_MS=8000 -DDEEP_SLEEP_AFTER_MS=15000" pio run -t upload`. While it sleeps COM7 disappears, so twist to wake it before flashing.

## Battery, calibration and the secret menu (src/battery.cpp, ui.cpp)

- `battery::` owns the supply reading (5 s samples, 0.7/0.3 smoothing), USB detection with hysteresis (USB above 4.30 V, battery below 4.22 V; USB sags to ~4.36 V under boot load) and V → %. The generic Li-ion table is used until a measured curve exists in NVS (`battery/curve`, 11 × uint16 mV at 0..100 %).
- Calibration: Start (secret menu) arms it; logging starts once USB is unplugged. While armed or running there's no screen timeout and no sleep (constant load). Every 30 s it appends `{uint32 t_s, uint16 mV, uint16 0}` to LittleFS `/cal.bin` (partition `spiffs`), opening and closing the file each time. NVS `calState`=Running at boot means the battery died: `processLog()` assumes constant current, so SoC = 1 − t/T, smooths over 5 samples, interpolates 11 points and enforces monotonic order. Runs shorter than 30 min or ending above 3.5 V are rejected. Verified with a synthetic linear log (`-DCAL_SELFTEST`, `cal synth`): output within 2 mV of exact.
- First calibration (2026-11-07, 700 mAh cell, full load): 3 h 31 min ≈ 200 mA average. 4.12 V → 3.3 V at 93 % of the runtime, then it collapses to the 2.6 V brownout within ~15 min. Curve (mV at 0..100 %): 2669 3331 3438 3521 3632 3705 3758 3813 3883 3930 4091.
- Low-battery cutoff (`LOW_BATT_*` in config.h, battery only): 3 consecutive 5 s samples below 3.30 V under load → `battery::empty()` → main loop shows "Battery low" (`ui::showLowBattery`, on `lv_layer_top`, works without `ui::begin`) for 3 s, then deep sleeps. This overrides calibration and the menu. On USB (unless `LOW_BATT_ON_USB`) it shows the message, clears the latch and carries on: **the knob never deep sleeps on USB**, it only turns the screen off. An `RTC_DATA_ATTR` latch makes later wakes call `battery::bootIsEmpty()` first in `setup()`; until the unloaded cell is ≥ 3.45 V or USB is plugged in, the knob only does `hal::begin` + message + sleep, with no Wi-Fi. `percent()` is rescaled so 0 % = the cutoff. `batt low` on serial forces the cutoff. Bench test of the boot path: `-DLOW_BATT_ON_USB=1 -DLOW_BATT_CUTOFF_MV=4700 -DLOW_BATT_RECOVER_MV=4800 -DLOW_BATT_MESSAGE_MS=15000`. The long message is the window to reflash.
- Serial commands: `cal status`, `cal dump` (CSV t_s,mV), `cal reprocess`, `cal reset` (clears curve, log and last result), `batt low`.
- Secret menu: hold a finger still (<25 px movement) within 90 px of centre for 10 s (`hal::centreHoldMs`) to toggle. It's on `lv_layer_top`, so swipes don't reach the pages, and the dial is ignored while it's open. It shows `v` + `FW_VERSION` (config.h) + `GIT_HASH` (from `scripts/git_version.py`, `+` = uncommitted changes), Wi-Fi SSID/RSSI/IP, each bulb with its IP and reachability, and battery V and curve type, followed by the calibration controls.

## Tapo KLAP v2 (as implemented in `src/tapo_klap.cpp`, verified against python-kasa)

- `auth_hash = SHA256(SHA1(email) || SHA1(password))`
- handshake1: POST `/app/handshake1` body `local_seed`(16) → `remote_seed`(16) || `SHA256(local || remote || auth)`. Capture the `TP_SESSIONID` cookie and the `TIMEOUT` value from `Set-Cookie`.
- handshake2: POST `/app/handshake2` body `SHA256(remote || local || auth)`
- `x = local || remote || auth`. `key = SHA256("lsk"||x)[:16]`. `ivseq = SHA256("iv"||x)`, so `iv = ivseq[:12]` and `seq = int32_be(ivseq[28:32])`. `sig = SHA256("ldk"||x)[:28]`.
- request: `seq++`. AES-128-CBC/PKCS7, IV = `iv || be32(seq)`. Body = `SHA256(sig || be32(seq) || ct) || ct`. POST `/app/request?seq=<seq>` with the cookie.
- **response = 32-byte signature || ciphertext.** Skip the 32 bytes and decrypt with the same IV.
- Envelope: `{"method":…,"params":{…},"request_time_milis":…,"terminal_uuid":…}`; the reply is `{"error_code":0,"result":{…}}`.
- `get_device_info` result: `device_on`, `brightness`, `hue`, `saturation`, `color_temp` (0 = colour mode), `nickname` (**base64**), `model`.
- `set_device_info`: send only the changed fields. Hue/sat must include `"color_temp":0` to leave white mode.
- On HTTP 403 or decrypt failure, re-handshake once. Re-handshake proactively 20 min before cookie `TIMEOUT`.
- "Third-Party Compatibility" must be on in the Tapo app.
- Not available locally: Tapo app *Smart Actions/automations* (cloud-side; the H100 hub and bulbs return errors for schedule/scene queries). Available on bulbs: `get_preset_rules` (the app's saved colour presets), `get_countdown_rules`, light effects.
- Any protocol change must keep `pio test` green. Regenerate vectors with python-kasa if the protocol changes.

## Engineering conventions

- **Never block the LVGL loop on the network.** The UI calls `lights::set*()`, which updates the cache optimistically and queues the change. The service task sends at most one request every 150 ms per bulb. Polls taken before a newer local change are discarded, so the UI never snaps back.
- Each request is a fresh TCP connection (`Connection: close`).
- Never commit credentials, and never print the password or auth hash to serial.
- `Resources/` is the read-only vendor reference: copy, don't build from it. It contains vendor `.exe`/`.rar` files; don't run them.
- Discovery / diagnostics from the PC: `kasa discover list` (python-kasa) shows model, IP and encryption type without credentials.
